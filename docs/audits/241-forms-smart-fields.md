# #241 · Formularios y campos inteligentes

Auditoría estática del 17/10/2026 sobre `11a71500` (`codex/ui-audit-forms`). Fuente: [issue #241](https://github.com/dariodeoli/scale-os/issues/241), incluido su pedido completo consolidado desde #242. Alcance: formularios, estado y controles existentes en Scale; no se inspeccionó ni modificó el repositorio externo de OwnCoding UI. Este documento no implementa migraciones ni acredita pruebas de navegador nuevas. Backend/modelos tienen auditoría complementaria de otro agente; las referencias API aquí explican el comportamiento observado del consumidor y deben conciliarse con esa auditoría antes de implementar.

## Conclusión y canónicos propuestos

La base local ya existe. `Editor` compone RHF/Zod, campos tipados y `Dialog`/`FormActions`; `SaveActions` y `useSingleFlightSubmit` cubren formularios RHF específicos. Conviene consolidar sus contratos de interacción, error y normalización, conservar los formularios de negocio como composiciones y migrar por familia. No reemplazar el flujo de registro, el consentimiento ni una operación financiera con un formulario CRUD genérico sólo por parecido visual.

Canónicos elegidos para la fase siguiente, sujetos a los contratos de cada dominio:

- Contenedor/cierre/foco: `app/dialog.tsx` + `dialog-context.ts`, `SaveActions` y `FormActions`. Evitar nuevos pies de formulario o trampas de foco.
- Formulario declarativo CRUD: `app/operations.tsx::Editor`, ampliado sin incorporar permisos, endpoints ni reglas económicas. Formularios RHF complejos mantienen su esquema y usan la misma infraestructura de interacción.
- Campos visuales locales: `TextField`, `EmailField`, `PhoneField`, `PasswordField`, `AmountInput` y `SelectCustom`/`PersonSelect`. Son el punto de adopción de dependencias ya existentes, sin búsqueda de reemplazos externos en esta fase.
- Consulta RUC: `client-ruc.tsx` y la confirmación de `ClientEditor`, extraer sólo el patrón consulta→previsualización→aplicar/descartar. Las políticas de cliente y empresa permanecen separadas.
- Valores económicos enteros: `normalizeWholeMoney` únicamente donde el contrato del consumidor exige enteros; dinero decimal, cantidad y porcentaje mantienen contratos distintos.

## Comportamiento de formulario: evidencia y brechas

| Tema | Evidencia en la base | Acción antes de declarar unificación |
|---|---|---|
| Datos ante error | Editor conserva RHF y captura error sin reset; workspace conserva valores; registro conserva estado entre fallos/pasos | Mantener identidad DOM/controlada al aparecer errores, no cambiar keys por mensajes; probar error 400/409/500/red y posterior corrección |
| Error por campo | Zod genera mensajes con `aria-invalid` y descripción. `api()` en operations convierte respuesta fallida a `Error(data.error)`; Editor sólo `setError(message(e))`, workspace similar | Definir contrato tipado de error sólo si API lo ofrece; conservar error general. No deducir campo por texto traducido ni atribuir 403/409 al primer input |
| Validación y foco | RHF `handleSubmit` y campos registrados; Editor abre primera sección inválida y salta paso móvil. Controles compuestos se actualizan por `setValue`, no todos registran ref RHF | No asumir que abrir sección equivale a enfocar control. Probar primer error compuesto, sección cerrada y paso oculto en navegador; establecer adaptador ref/focus canónico |
| Límites | `Field.maxLength` se pasa a input/textarea, pero no se incorpora a Zod; required usa `min(1)` sin trim | DOM limita escritura ordinaria, no valores programáticos ni espacios solos. Conciliar mínimos/límites reales por consumidor y conservar validación servidor |
| Pending | Editor `saving.current` impide doble mutación; workspace hook bloquea incluso durante validación async; registro usa ref síncrona | Adoptar una semántica compartida. Login no tiene guard/busy en `login()` ni disabled en CTA: dos submits pueden hacer dos login/me/load (hallazgo estático, pendiente repro controlada) |
| Controles pendientes | Editor pasa disabled a nativos, dinero, teléfono, email y selectors. Rama PasswordField no recibe disabled, y ese componente no lo admite | La contraseña puede seguir editable mientras se guarda; añadir al contrato común tras prueba de consumidor. No afirmar que `aria-busy` deshabilita campos |
| Workspace pendiente | `SaveActions` bloquea cierre y CTA; algunos inputs registrados, opciones de estado/cuenta/moneda y BancoCombobox carecen de disabled/fieldset | Auditar captura consistente del payload frente a cambios durante petición. Deshabilitar conjunto de campos sin perder valores ni refs; no reescribir validación del dominio |
| Dirty/cancel | Editor registra `interacted && isDirty`, tras éxito resetea base; SaveActions registra dirty. Dialog agrega registros por form, bloqueo pending y confirmación nested para cerrar/Escape/fondo | Forms locales que no usan `useDialogPending`/SaveActions no adquieren protección automáticamente por estar en Dialog. Navegación fuera del diálogo no tiene protección genérica equivalente en estos componentes |
| Guardar/refrescar | Editor mantiene draft si save rechaza. `my-profile` distingue persistencia exitosa de fallo de refresh; otros consumidores pueden ejecutar varios PATCH secuenciales | No llamar fallo total a una mutación persistida. Cliente+plan son peticiones separadas: si falla la segunda, la primera puede estar guardada; UI debe reconocerlo sin repetir efectos |
| Pie y foco modal | Dialog restaura foco, gestiona stack y trap; FormActions asocia submit por `form` y no publica portal si ancestor details/hidden/inert cerrado | Conservar test browser real; `getClientRects()` solo no prueba visibilidad de contenido dentro de details cerrado |
| Reset/remount | Editor lee defaults al montar; algunos consumidores fuerzan key por id/updated_at/revisión; `EditorHandle.patchValues` conserva formulario para cuenta creada desde cobro | Refresco externo puede desmontar un borrador si cambia key: decidir política y probar antes de unificar. No sustituir patchValues por key/remount |

## Campos inteligentes y reglas observadas

### RUC y coincidencias existentes

`client-ruc.tsx::lookupRuc` normaliza y valida mediante las funciones importadas ya usadas por la aplicación; POST `/api/agency/ruc-lookup` sólo consulta. Un resultado nulo genera «No encontramos una ficha publicada… Podés cargar los datos manualmente». Error queda como aviso junto al campo y conserva ficha. `ClientEditor` mantiene la promesa pendiente mientras muestra `RucConfirmCard`: sólo Aplicar devuelve `{tax_id, legal_name}`; Descartar no escribe. La tarjeta muestra fuente/estado/fecha. No completa teléfono, email, dirección, ciudad ni documento porque **la respuesta tipada no aporta esos datos**. No se deduce persona jurídica, CI ni representante desde RUC.

Brecha a comprobar: mientras hay consulta o tarjeta, el usuario puede editar RUC/razón social y el save general no depende de `lookupBusy`; al confirmar, `runLookup` aplica el resultado con `setValue` sin comparar el valor de inicio ni qué campos cambiaron manualmente. Hay confirmación explícita, pero falta política visible de conflicto/stale result. No hay cancelación HTTP ni generación asociada al valor; desmontaje rechaza la promesa de confirmación, no cancela el proveedor. La consulta/aplicación tampoco participa por sí sola en `interacted` si el disparador es programático.

La ayuda/comentario cliente describe 5–8 dígitos con DV opcional; el límite visual es 14. La evidencia local de `backend/ruc-lookup.js` difiere por operación/proveedor: normalizador general 3–12 dígitos, OwnData hasta 9 sin cero inicial y DV validado. No establecer un nuevo regex global a partir de comentarios: conciliar regla de guardado, consulta y proveedor con auditoría backend.

`assertUniqueClientRuc` en backend bloquea duplicado por empresa con 409 y no revela registros de otra empresa; CREATE y PATCH usan mutex de organización. La UI actual no muestra un dropdown de clientes existentes desde email/teléfono/RUC y no transforma ese 409 en selección de ficha. Email/teléfono no son evidencia de unicidad del cliente. Propuesta: resultado de búsqueda interna autorizado y acotado al tenant, mostrado con identidad canónica; elegir registro y seguir manual son decisiones del consumidor. No exponer búsqueda global de usuarios/empresas ni convertir nombre parecido en identidad.

Empresa (`suite.tsx`) conserva RUC texto libre de 60, sin lookup ni confirmación. También hay desajustes de límite confirmados en empresa: nombre visual120 frente a160 en `agency-suite.js`; perfil legal visual120 frente a160 para ciudad/departamento/nombre/cargo y documento visual80 frente a60 en `contracts.js`. No existe selector de empresas fiscales por coincidencia en ese formulario. Diferencia deliberada hasta validar contrato; no imponer lookup obligatorio ni normalización irreversible de documentos legacy.

### Ciudad, departamento y dirección

`client-editor-data.ts` y `company-legal-profile.tsx` usan texto libre ciudad/departamento de 120. Dirección cliente/empresa tiene 400; no se halló en estos consumidores un catálogo local ni relación país→departamento→ciudad. No hay autoderivación actual que acreditar. Elegir una fuente de datos separada de la UI antes de diseñar el selector, conservar entradas manuales/legacy y valores fuera del catálogo. Una ciudad homónima no debe sobreescribir departamento sin confirmación. Ciudad de firma de contrato tiene otro propósito y no debe vincularse automáticamente al domicilio.

### Email y teléfono

- `EmailField` es canónico local con autofill y sugerencias de dominios (`field-rules.ts`), que son sugerencias sintácticas, no coincidencias verificadas ni existencia de cuenta. Devuelve texto tal como se escribió; no lowercasing silencioso durante caret.
- Diferencia comprobable: input `maxLength=200`; `emailValid` y `backend/suite-validation.js::email` admiten 254. Campo visual debe aceptar lo que su endpoint admite; no reducir backend por uniformidad. Además, sin `id` (registro/login) el datalist usa id vacío: verificar asociación accesible y unicidad antes de migrar.
- `PhoneField` ofrece +595/+55/+54/+1/+34, elimina ceros iniciales, recorta local a 12 y compone `+código dígitos`; PY acepta 8 fijo/9 móvil según `phoneValid`. Backend también admite +598/+56/+57/+51/+52/+591/+351. Una ficha existente con país no incluido cae visualmente al +595; evitar guardar una identidad telefónica distinta al editar otro dato. No migrar ni ampliar países sin casos de parseo/roundtrip y contrato acordado.
- Ambos admiten vacío según la regla del consumidor; invitación/acceso y correo de contacto no tienen la misma obligatoriedad ni consecuencias.

## Selectores y accesibilidad relacionadas con formularios

`SelectCustom` escoge PersonSelect por metadata o regex del label. La elección de modelo no debería depender de traducción («responsable», «custodio»): proponer variante explícita manteniendo compatibilidad mientras se migran consumidores. `PersonSelect` y `EntityPicker` de personas convergen; EntityPicker de registros mantiene búsqueda y contexto en lista de botones, PlainSelect usa listbox flotante. No forzar selector de cuenta/factura con saldo a perder ese contexto ni convertir menú de acciones en listbox.

PersonSelect coloca `aria-invalid`/`aria-describedby` en wrapper; comprobar que el combobox real recibe o anuncia el error antes de asumir equivalencia con PlainSelect. Editor choices no vincula `Field` con ref RHF para foco. Los selects nativos del país y los pickers del navegador tienen interacción propia con Escape; preservar el manejo existente de overlays. Auditoría JSX global complementaria debe decidir API y tokens definitivos.

## Secuencia de migración propuesta, sin implementar

1. Conciliar esta matriz con inventario visual y contratos backend de #241. Fijar por campo valor canónico, límite, vacío, min/max, error y fuente. Registrar excepciones empresa/cliente/usuario, porcentaje/dinero entero/decimal, fechas civiles/timestamps.
2. Definir contrato común de interacción: pending síncrono, error general+field errors tipados cuando existan, registro dirty, foco/ref, successful-save vs refresh-failure. Mantener compatibilidad del Editor y sus 25 archivos consumidores.
3. Corregir primero brechas verificables (límites, países legacy, password pending, login single-flight, refs de compuestos); cada cambio con issue/criterio y pruebas focales, sin mezclar rediseño de negocio.
4. Extraer consulta confirmable genérica con cancelación/generación y resolución de conflictos de edición; mantener mappers/provider/permiso tenant en Scale. Adoptar en cliente primero, empresa sólo tras su contrato explícito.
5. Migrar wrappers/campos y formularios por familia, usar el mismo Dialog/FormActions/SaveActions y mantener esquemas complejos independientes. Revisar que no queden variantes muertas antes de eliminarlas.
6. Catálogo local: vacío/completo/error/pending/readonly, foco real y dark/light a1366×768 y390. Sólo tras unificación local decidir qué puede documentarse/publicarse externamente. Esta etapa no cambia dependencias.
